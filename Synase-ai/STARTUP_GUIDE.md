# SYNASE AI Startup Guide

This guide explains how to clone, validate, build, serve, inspect, and troubleshoot the SYNASE AI frontend.

## 1. Current runtime model

SYNASE AI `0.12.0` is a static, dependency-free frontend prototype built with HTML, CSS, and JavaScript modules.

- The checked-in application runs against deterministic mock domain services.
- No live backend or external provider is connected.
- Running the project does not initiate AI execution, repository changes, CI/CD changes, infrastructure actions, publication, or deployment.
- The `dist/` directory is generated by the build script and can be served by any static web server.

## 2. Prerequisites

### Required

- Git, when cloning the repository
- Node.js with ES modules and the built-in `node:test` runner
- npm, which is bundled with Node.js

Node.js 24 is the validated CI version and is recommended.

Check your tools:

```bash
git --version
node --version
npm --version
```

### Optional

- Python 3 for the example static server
- Any alternative static server capable of serving `dist/`

```bash
python3 --version
```

## 3. Get the source

```bash
git clone https://github.com/satyam022028singh/Synase-ai.git
cd Synase-ai
```

Verify the branch and revision:

```bash
git status
git rev-parse HEAD
```

The authoritative release history is on `main`.

## 4. Dependency setup

The current `package.json` contains no third-party dependencies. You do not need to run `npm install` to use the checked-in test and build scripts.

If dependencies are added later, install them using the lockfile committed by that future version. Do not create or replace a lockfile without an explicit dependency change.

## 5. Validate the baseline

Run all contract tests:

```bash
npm test
```

Expected Phase 12 baseline:

```text
64 tests
0 failures
```

Then build the production output:

```bash
npm run build
```

Expected result:

```text
Built SYNASE AI frontend (13 assets) → dist/
```

Inspect the generated manifest:

```bash
cat dist/build-manifest.json
```

The manifest should include Phases 0–12 and hashes for the application entry, shared assets, Phase 11 assets, and Phase 12 assets.

## 6. Start the application

### Option A: Python static server

```bash
python3 -m http.server 4173 -d dist
```

Open:

- [http://localhost:4173](http://localhost:4173)
- [http://localhost:4173/#/app/dashboard](http://localhost:4173/#/app/dashboard)

Stop the server with `Ctrl+C`.

### Option B: Node-based static server

If your environment already provides a static server, point its document root at `dist/`. Do not serve the repository root for production-like checks when `dist/` is available.

Example with an existing `serve` command:

```bash
serve dist -l 4173
```

This repository does not declare `serve` as a dependency, so do not expect that command to exist unless your environment provides it.

## 8. Mock mode

The shipped application composition uses deterministic mock data.

Mock mode guarantees:

- no backend request is required to render the application
- no external provider is contacted
- no records are imported
- no credentials are requested
- no downstream action is executed
- stable identifiers and state are available for contract tests

Visible mock labels and provisional-route labels are intentional safety behavior. Do not remove them merely to make the prototype look live.

## 9. Live adapter development

Phase 12 includes a live service boundary in `src/phase12-api.js`:

```js
import { createPhase12Service } from "./src/phase12-api.js";

const dashboardService = createPhase12Service({
  mode: "live",
  baseUrl: "https://api.example.com",
  fetchImpl: globalThis.fetch,
  timeoutMs: 8000
});
```

Important constraints:

1. The checked-in application does not automatically switch to live mode.
2. Do not place tokens, passwords, API keys, cookies, or secret-manager values in frontend code or public environment values.
3. The base URL must use HTTPS, except for `http://localhost` and `http://127.0.0.1` during local development.
4. The current live dashboard request is read-only: `GET /api/v1/dashboard`.
5. Authentication/session behavior is unresolved. The service uses browser credentials mode but does not define login, renewal, logout, or callback behavior.
6. A successful frontend build is not evidence that the backend is connected or authorized.
7. Keep mock and live adapters interface-compatible.
8. Do not add browser-side joins to compensate for missing aggregate endpoints.

Before enabling live composition, freeze:

- authentication and session contracts
- dashboard aggregate DTOs
- authorization/capability fields
- standard errors and nullability
- pagination and idempotency policy
- request/correlation behavior
- deployment-specific CORS and cookie policy

## 10. Development workflow

Recommended change sequence:

```bash
# 1. Create or select a branch
git switch -c feature/your-change

# 2. Edit source files under src/ and tests under test/

# 3. Run validation
npm test
npm run build

# 4. Review changes
git diff --check
git status

# 5. Commit
git add README.md STARTUP_GUIDE.md src test scripts index.html package.json
git commit -m "feat: describe your change"
```

Only add paths that actually changed. Generated `dist/` and release packages are produced by the GitHub Actions workflow on `main`.

## 11. Production build contents

`npm run build`:

1. removes the old `dist/`
2. recreates the output directory
3. copies `src/` and `index.html`
4. calculates each production asset's byte size and SHA-256 digest
5. writes `dist/build-manifest.json`

Because the build is static, deployment normally consists of serving the contents of `dist/` from a static host or CDN. Deployment configuration is not included in this repository, and no deployment should be claimed without an actual authoritative deployment result.

## 12. Validation evidence

The latest release evidence is stored in:

- `phase12-validation.json`
- `dist/build-manifest.json`

Use `git clone` or `git pull` to obtain the complete project. Generated ZIP archives are intentionally excluded from version control.

`phase12-validation.json` records:

- validated source commit
- test pass/failure counts
- production build result
- backend-connected status
- external-system contact status for mocks
- secret-exposure status
- downstream-execution status
- UTC validation timestamp

GitHub Actions is the authoritative combined test/build run for the packaged release.

## 13. Browser QA checklist

For UI changes, check at minimum:

- desktop around `1440×900`
- laptop/tablet around `1024×768`
- mobile around `390×844`
- reduced-motion preference
- keyboard-only navigation
- visible focus
- one semantic page heading
- accessible control names
- responsive tables and drawers
- text/icon status in addition to color
- no horizontal viewport overflow
- no clipped controls
- no stuck overlays
- no console errors or unhandled rejections
- no exposed secrets or raw authorization material
- no copy that implies unconfirmed execution

## 14. Troubleshooting

### `npm test` fails

1. Confirm the Node version:

   ```bash
   node --version
   ```

2. Ensure you are in the repository root.
3. Confirm test files exist:

   ```bash
   ls test
   ```

4. Run one test file directly:

   ```bash
   node --test test/phase12.test.mjs
   ```

5. Do not update fixtures merely to hide a contract regression.

### `npm run build` fails

1. Confirm these files exist:

   ```bash
   ls index.html scripts/build.mjs src
   ```

2. Check JavaScript syntax:

   ```bash
   node --check scripts/build.mjs
   node --check src/phase12-api.js
   node --check src/phase12.js
   ```

3. Remove only generated output and rebuild:

   ```bash
   rm -rf dist
   npm run build
   ```

### Page is blank

1. Serve `dist/` over HTTP; do not rely on directly opening `index.html` with a `file://` URL.
2. Open browser developer tools and check the Console and Network panels.
3. Confirm module files return HTTP 200 responses.
4. Confirm the URL includes a valid hash route such as `#/app/dashboard`.

### Port 4173 is already in use

Use a different port:

```bash
python3 -m http.server 8080 -d dist
```

Then open [http://localhost:8080](http://localhost:8080).

### GitHub cannot be resolved

Check DNS and remote access from your own environment:

```bash
curl -I https://github.com
git ls-remote https://github.com/satyam022028singh/Synase-ai.git refs/heads/main
```

If your managed execution environment blocks outbound network access, use an authorized GitHub integration or work from an uploaded source package. Do not paste GitHub tokens into chat, source files, or command history.

### Dashboard says the aggregate contract is unresolved

That message is expected. The Phase 12 mock dashboard intentionally labels its selected-project composition because a workspace-level aggregate contract has not been frozen.

### Live mode reports `LIVE_API_NOT_CONFIGURED`

That is fail-closed behavior. Configure and wire a live service only after the backend contract and safe deployment configuration are approved. Do not bypass the check by embedding credentials or hard-coding an untrusted endpoint.

## 15. Security notes

Never commit or expose:

- passwords
- API keys
- OAuth tokens
- authorization headers
- cookies or session material
- MFA secrets
- private keys
- signed-upload credentials
- secret-manager values
- complete sensitive request or response payloads

Use safe references, request IDs, redacted metadata, and backend-authoritative outcomes instead.

## 16. Release checklist

Before describing a release as complete:

- [ ] all existing tests pass
- [ ] new contract tests cover the change
- [ ] production build passes
- [ ] build manifest includes the expected phases/assets
- [ ] desktop, tablet, and mobile QA pass
- [ ] accessibility and reduced-motion checks pass
- [ ] secret and payload safety checks pass
- [ ] mock/live boundaries are documented
- [ ] unresolved contracts remain explicit
- [ ] source commit is pushed
- [ ] GitHub Actions validation succeeds
- [ ] validation JSON and package are generated
- [ ] handoff documentation records the final commit

## 17. Current limits

SYNASE AI is frontend-complete through Phase 12, but it is not yet a live production system. Backend connectivity, authentication, persistence, external synchronization, notification delivery, security-grade audit guarantees, publication, and deployment require authoritative backend and operational contracts.
